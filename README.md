# dsh-guide

DSH 的「运行中引导」插件：Agent 干活的时候你在对话框里补一句话，它不会把这句话当成新任务推倒重来，而是当作对当前任务的引导。会话头右侧有一个状态徽标，点一下即可开关。

## 它解决什么

默认语义下，工作中插话会以一条普通用户消息进入模型上下文（`steer` 进当前回合，`queue` 进下一回合）。模型看到「user: 一句新要求」，常见的反应是丢掉当前进度、按新要求重做。

dsh-guide 不改变你已经发出的消息，也不改动它的投递方式。它只做一件事：在这条消息真正进入模型上下文的那一步之前，插入一条 `notice` 形态的说明：

> 用户在你执行当前任务期间补充了下面的消息。请把它当作对当前任务的引导，而不是一个新任务：保留已经完成的工作，不要重来、不要重复已完成的步骤；只调整这条指引真正涉及的部分，然后继续当前任务。

模型因此读到「引导」，而不是「新任务」。聊天记录里你的原文保持不变，只是多出一条可折叠的「运行中指导」上下文行。

## 开关与徽标

会话头右侧有一个「● 引导」徽标：

- **开着**：绿点、正常文字，表示运行中插话会被改写成引导；
- **关着**：灰点、次级文字，表示完全不做干预；
- 徽标后面的数字是**本次会话已注入的引导条数**。

点徽标切换开关。关闭时同时撤掉那条常驻 system prompt 规则，所以模型连"引导"这个概念都看不到。状态按 profile 持久化在 `$DSH_HOME/dsh-guide.state.json`，重启后保持。

## 让"没打断"看得见

只保证行为不够，还要让人当场感觉到。插话后，输入框正上方会出现一条状态条，两个阶段各出现一次：

| 时机 | 文案 | 含义 |
|---|---|---|
| 你按下发送、消息进入运行中的回合 | 已作为引导送达 | 收下了，回合还在跑 |
| 模型在小步边界真正读到它 | 引导已读入 | 已经生效 |

状态条 8 秒后自动消失；同时会话头的徽标会闪一下绿色光圈，计数 +1。状态条和徽标都只读宿主记录的 `interjectedAt` / `injectedAt` 时间戳，不猜测、不伪造。


## 覆盖范围

| 你的发送方式 | Agent 状态 | 是否注入引导说明 |
|---|---|---|
| 忙碌时 Enter 投递模式为 `steer`（插话） | 运行中 | 是，当前回合内被读到 |
| 忙碌时 Enter 投递模式为 `queue`（排队） | 运行中 | 是，下一回合开始时被读到 |
| 空闲时正常发送 | 空闲 | 否，普通新任务 |
| 任意 | 开关关闭 | 否 |

## 数据通道

全部只接受本机回环地址：

| 路由 | 用途 |
|---|---|
| `GET /dsh-guide/state?session=<id>` | `{enabled, revision, injected}` |
| `POST /dsh-guide/toggle` | `{enabled?, sessionId?}`，省略 `enabled` 表示取反 |

客户端每 3 秒对一次状态，点徽标时立即更新。

## 实现边界

- 只用公开扩展点：`agent/inbox/inserted`、`agent/inbox/discarded`、`agent/disposed`、`agent/pre-step`、`ctx.systemPrompt.section`、`webServer`。
- 不 import 任何 `@deepseek-ai` 包。
- 注入的消息是 `source.kind = 'dsh-guide'` 的用户角色消息，和官方 `model-selection`、`repeat-tool-reminder` 等上下文注入同形；因此不会被当成用户发言，也不参与 `rpcId` 幂等判断。
- 只跟踪「插入时 Agent 正在运行」的用户消息，最多记住 256 条，命中即删。

## 已知限制

- 这是提示词层面的引导，不是硬约束：模型仍可能选择重排计划。说明写得越靠近消息、越明确，遵从度越高。
- 如果工作流本身要求「插话即改需求」，关闭徽标或先停止当前回合。
- 只处理 `source.kind === 'user'` 的消息，子代理之间互发的 `agent-message` 不在此列。
